# R1 — Foundations and front door (v0.7.0)

The first release of Phase R (`70-redesign-overview.md`). It lays the deck's visual foundation
under the whole app and rebuilds everything a person sees before they reach a console: sign in,
forgot password, join, change password, the four system pages and the splash. It also adds the
one maintenance mechanism the programme uses. R0's groundwork (deck import, docs rewrite, gap
register) rides to production in the same version.

Nothing inside a console is rebuilt. The old teacher and student consoles take the new palette,
font and focus ring and keep their layout and geometry, because the primitives are additive
(ordering rule 1, D7). Screens are compared with `docs/design/deck/Quizzivy Sign in.dc.html`
(`#login`, `#forgot`, `#join`, `#joined`, `#change`), `Quizzivy System pages.dc.html` (`#404`,
`#403`, `#error`, `#maintenance`) and `Quizzivy Splash.dc.html` (`#loading`, `#skeleton`,
`#slow`, `#offline`, `#update`, `#expired`). Design gaps are cited by DG id from
`docs/design/gaps.md`.

**Deliverable:** deck tokens (light and dark), Be Vietnam Pro, motion, icons and additive
primitives; the rebuilt front door, system pages and splash; maintenance windows end to end
(operator command, public status, 503 gate, deadline extensions a running attempt picks up).
**Exit criteria:**
- every front-door, system and splash screen matches the deck at 360, 768, 1024, 1280 and 1440,
  light and dark, measured in the browser;
- every old `/admin` and `/app` route keeps its layout at 1280 and 360, in light, with the new
  palette and font;
- a maintenance window rehearsed locally end to end: scheduled with `cmd/maintenance`, the SPA
  shows the maintenance page, an attempt in progress is extended and its timer shows the new
  deadline after the window, a start that would overlap is refused;
- every CI step green locally and in CI, E2E chromium and live green;
- released to production as `v0.7.0`.

**Decisions taken in this file, worth a second look.**

- **Deck geometry is scoped by `data-scale="deck"`, not by call site.** Colours, font and the
  focus ring change globally. Control heights, paddings and the `sm`/`md`/`lg` radii that differ
  from today apply only inside an element carrying `data-scale="deck"` (Tailwind v4's `in-data-*`
  variant, and `--radius` redefined in that scope). Rebuilt surfaces set it on their root: the
  front door and system pages in R1, each console as it is rebuilt. This is what "additive"
  means in practice: an old screen cannot shift because no class it renders changes meaning.
  R5 deletes the scope and makes the deck geometry the default (the "primitive defaults flip").
- **No theme control ships in R1.** The preference (`light | dark | system`, default `light`,
  the deck's `startTheme`) and the boot script exist, and the front door honours them, but the
  only surfaces the deck gives a toggle are the console top bars, account menus and Settings ›
  Appearance, all rebuilt in R3–R5. Old consoles force light while mounted, so a dark
  preference set later in the student app (R3) cannot paint the old teacher console half dark
  (D7). Dark is verified in R1 through the test harness.
- **Deck token names are kept verbatim on `:root`**, so deck CSS diffs against ours. The lime is
  `brand` in utilities (`bg-brand`, `text-brand-ink`) because shadcn's `accent` already means
  the hover surface. The legacy shadcn and semantic names (`destructive-ink`,
  `*-foreground`) stay as aliases until R5 rather than sweeping old screens now.
- **Three tokens go beyond the deck, for accessibility** (DG-30, DG-31): `--focus` (the focus
  ring, set to `--muted-fg`: 5.4:1 on white, 7.1:1 on the dark background), a darker `--input`
  border (`#8a9395` light, 3.1:1; `#5d6769` dark, 3.2:1) and `--danger-solid`
  (`oklch(0.55 0.2 27)`, about 5.4:1 under white text) for destructive buttons. The deck's
  `--ring` (2.6:1) and `--border` (1.25:1) stay for what the deck uses them for. The token test
  measures all three, so a design answer that changes them fails loudly rather than silently.
- **One maintenance mechanism, written only by the operator.** `app.maintenance_windows` is
  created by a migration and written only through `cmd/maintenance` under
  `MAINTENANCE_DATABASE_URL`; the app role gets `SELECT` and nothing else. There is no
  `MAINTENANCE_MODE` environment switch and no admin endpoint: the deck draws no control
  (DG-42), and a table the API cannot write cannot be turned on by a compromised session.
- **Extensions are applied when the window is scheduled**, in the same statement that inserts
  it, audited as System (`actor_user_id` NULL). Every in-progress attempt whose deadline falls
  after the window's start gains the window's length; every assignment that closes inside the
  window gains the same. Doing it at scheduling time needs no timer in the API and cannot be
  skipped by a process that was asleep at the start. Cancelling or ending a window early keeps
  the extensions: giving time back is harmless, taking it back mid-test is not.
- **No new attempt may overlap a window.** Starting one whose deadline would pass a scheduled
  window's start answers `409 MAINTENANCE_SCHEDULED`; resuming is never refused. The start and
  the scheduling serialise on one advisory lock, following the `LockForDraftUse` /
  `LockForVersionUse` precedent, so no attempt slips between them.
- **The 503 gate exempts no role and covers the integrity beacon.** An admin exemption needs
  the principal, which exists only after auth, and a role model R2 replaces; the operator ends a
  window early instead. Events the beacon would send during a window are dropped, and the
  client pauses integrity capture while the maintenance or session-expired overlay shows, so a
  student is never flagged for looking away from a page that told them to wait.
- **A running attempt learns a moved deadline.** Today the client takes `deadlineAt` only from
  the session payload, so an extension (a teacher's Extend, or maintenance) reaches an open tab
  only after a reload, and its local timer submits early. R1 returns `deadlineAt` from every
  autosave and refuses a `timer_expired` submit that arrives more than five seconds before the
  server's deadline (`409 DEADLINE_NOT_REACHED`); the store adopts the server's deadline from
  either. Without this, maintenance extensions would be granted on the server and lost in the
  browser.
- **Unavailable is not signed out.** A refresh that fails because the network is down or the API
  answers 503 no longer signs the user out; only a refused refresh does. Today an offline cold
  load lands on `/login`, and maintenance would do the same to every open tab.
- **App states are overlays over a mounted route, not routes.** Maintenance, session expired and
  update render above the current page (made `inert`), so an attempt stays mounted beneath with
  its local draft. The deck's "Check again" reloads the page; ours re-reads the status and
  closes the overlay, for the same reason. The update prompt waits for the next navigation and
  never appears on the take-test route.
- **Joined is a state of `/join/:code`, not a route.** `70-redesign-overview.md` §5 lists the
  front-door routes and has no `/joined`; the success step lives in the join route's location
  state (it survives a reload). `/join/:code/confirm` redirects, so printed QR codes and old
  links keep working.
- **Password rules are a schema constraint.** `newPassword` gains
  `pattern: '[\p{N}\p{P}\p{S}]'` (a number, punctuation or symbol character; a Vietnamese letter
  is a letter), enforced once by `httpx.ValidateRequests`. "Different from the temporary
  password" becomes `PASSWORD_UNCHANGED`, applied to every change (for an ordinary change it is
  a comparison with the verified current password). Existing passwords are never re-validated.
- **Organisation details come from build-time config.** The org name (brand panel,
  system-page caption) and the front-desk phone and hours (Forgot password) are `VITE_ORG_*`
  values, each line hidden when unset (DG-41). The build values stay after R5: R5's Organization
  settings take precedence on the front door, which falls back to these values when a setting is
  empty or the API is unreachable, and they are the Landing's contact source (R11). R11 adds
  `VITE_ORG_EMAIL` and `VITE_ORG_ADDRESS` (T-R11.4b); no release removes them.
- **The join page sends at most one preview per distinct complete code**, as today's confirm
  page does. The re-budget of the join and login limits for a class behind one school NAT stays
  in R2, as the approved plan places it; R1 does not raise request volume, and a unit test pins
  that.
- **The §6 alphabet string is authoritative.** `ABCDEFGHJKLMNPQRSTUVWXYZ23456789` contains `L`;
  the spec's "(no `1/I/L`)" and DG-02's "no … L" are wrong, and both the client
  (`features/join/code.ts`) and the server (`classes/domain/joincode.go`) use the string. The
  R1 docs task corrects the prose.
- **The read side lives in a new `availability` module**: the window query, the status
  endpoint and the start guard. R5's `organization` module may absorb it; nothing else depends
  on the name.
