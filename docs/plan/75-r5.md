# R5 — Admin console and email (v0.12.0)

The release that gives `/admin/*` to the Admin console the deck draws in
`docs/design/deck/Quizzivy Admin.dc.html`, and that brings email. It is the first release in which
a second teacher can be created from the product (70 §2 rule 2), so it runs after R2
(`72-r2.md`: roles, permissions, the principal cache, ownership scoping and the subset,
student-target and last-admin guards) and after R4 (`74-r4.md`: the console shell and composites,
in-app notifications, profile and preferences, `platform/tabular`, `platform/imagesafe`,
`platform/uaparse`, and the rotation of every legacy join code).

The Admin deck has no hash routes: its screen is the prototype's `route` state (`overview`,
`users`, `roles`, `classes`, `audit`, `apiref`, `settings`), set for comparison through
`localStorage['qz-admin'] = {"route":"users","dark":false}`. Design gaps are cited by DG id from
`docs/design/gaps.md`. Outside the console, the teacher and student sides change only where this
file says so: the workspace switcher gains its "Admin console" row, class screens say when joining
by code is off, a removed answer reads as removed, and the Students page's "Last active" becomes
true.

Resend lands here with its first consumers (70 §2 rule 6): set-password links (D15), sign-in
invitations and the data-export notice. The notification platform keeps its in-app channel until
R7 adds email to it.

**Deliverable:** the Admin console (`AdminLayout`, Overview, Users with the user sheet, Add user,
import and bulk actions, Roles & permissions, Classes across teachers, Audit log, API reference,
System settings with Organization, Sign-in, Data & privacy and Plan & usage) and the backend it
needs: the `organization`, `audit` and `exports` modules, admin user and role management under the
subset rule, activity tracking, content transfer for offboarding, user-import and data-export jobs
in the worker, `platform/email` with Resend and the outbox, set-password links, the sign-in
policy with lockout validation, and the nightly retention sweep under its own database role. The
primitives take the deck's geometry as their default.

**Decisions taken in this file, worth a second look.**

- **Credentials leave the server in one of two ways, chosen per action.** Add user, Reset
  password (one or many) and user import each offer "Email a set-password link" (the default
  when email is configured) or "Show a temporary password" to hand over in person. D15 forbids a
  password in an inbox, not on a slip handed to a child in class. The deck draws this toggle only
  on the import dialog ("Email sign-in details"); the same toggle is added to Add user and Reset,
  with the wording DG-05 asks for. A temporary password is never written to the outbox, a log or
  object storage.
- **The set-password token travels in the URL fragment, and using it signs the user in.**
  `…/set-password#token=…` never reaches a server log, a proxy or a `Referer`, and the page removes
  it from the address bar before its first request. Only the SHA-256 of a 256-bit token is stored;
  the raw token exists only as outbox ciphertext until the message is sent. Every invalid state
  answers one identical `410`. Setting the password returns a session the way sign-in does, since
  the link has just proved control of the mailbox, and ends the account's other sessions, since a
  reset should.
- **Resend over `net/http`, with no SDK.** Sending is one authenticated POST carrying an
  `Idempotency-Key` (the outbox row id). That is about a hundred lines, against a new dependency.
- **Email is text-first: no images, no tracking, click tracking off in Resend.** Gmail does not
  render SVG and many clients block remote images; click tracking would pass the set-password
  token through Resend's redirector. The organization's name heads every message.
- **The outbox drains from both processes, within a daily budget.** The API and the worker each
  run a dispatcher woken by their own enqueues and by a timer armed only while a row is pending,
  so an empty outbox never wakes Neon (#134, #143). `EMAIL_DAILY_LIMIT` (default 100, Resend's
  free tier) moves the excess to the next local day, and the import dialog says so before a large
  send (O-R5.1).
- **Heavy work runs in the worker; parsing stays in the API.** An import preview parses at most
  5 MiB and 2,000 rows under a one-slot semaphore and writes nothing. The accepted rows, not the
  file, are stored; the worker creates accounts and hashes passwords under
  `MAX_CONCURRENT_PASSWORD_HASHES`. Data exports are written to the worker's disk, then to the
  private bucket. Both jobs wake the worker through `IMPORT_WORKER_WAKE_URL`, as imports do.
- **The hand-out sheet is assembled at download, once.** Each row's temporary password is sealed
  with a `SECRETS_KEY`-derived key as its row commits, so a worker crash loses nothing. The first
  download decrypts, streams and erases them, and after 24 hours nothing is readable.
- **A data export is fetched from an app page, by its requester, up to three times (D-024).** The
  email links to `/admin/exports/{id}`, never to an object. The download needs the requester's
  session and `system.data_export`, returns a presigned URL valid for 60 seconds, counts the
  signing in `downloads`, and the fourth request, or any after 24 hours, answers `410`. The deck's editable "Send the link to" becomes the requester's own address, read-only: a
  notice about a full export of personal data has no reason to go anywhere else (O-R5.3).
- **The nightly sweep runs from GitHub Actions under a new `quizzivy_maintenance` role.** Fly
  secrets are visible to every process group, so the API would see a credential stored there.
  The role holds only what `cmd/maintenance` needs, including R1's window commands (with R4's
  override close times) and R2's join-code rekey, so the owner credential leaves routine
  operations. A release that adds or widens a command grants exactly what it needs in its own
  migration and pins it in `privileges_test.go` (70 D16). The rekey runs from the operator's
  machine with both join-code keys and `MAINTENANCE_DATABASE_URL`, never from the workflow. The
  sweep wakes Neon once, at 03:00 local, and scheduled runs apply only once
  `RETENTION_SWEEP_ENABLED` is set after a reviewed dry run.
- **Ending access is one rule.** Every password reset (single, bulk, reset-link issue and link
  use),
  disable, sign-out-everywhere and role change does three things in one command: it revokes the
  user's refresh families, bumps `session_epoch` and calls `Principals.Forget(userID)`. A disable
  also revokes the account's unused set-password links in the same transaction, and enabling the
  account restores none (an Admin sends a new link through Reset).
  `setRolePermissions` and `updateRole` call `Principals.ForgetAll()`. The change applies on the
  next request to the machine that made it and within 10 seconds on any other (R2's cache).
- **The server enforces a temporary password.** While `must_change_password` is set,
  `RequirePermission` answers `403 PASSWORD_CHANGE_REQUIRED` to every operation except
  `getCurrentUser`, `changePassword`, `logout` and `refreshSession`; the flag travels in the
  cached principal. R2 deferred this to R5; it is the default pending Thuong (O-R5.4).
- **`deleteUser` stays student-only and has no console control.** Offboarding is disable, then
  transfer (R2 left the widening to R5).
- **Built-in role names render from `role.builtin.<key>` keys while the stored name is still
  the seeded one, else as stored.** So an English matrix reads "Teacher" until an Admin renames
  the role (R2 left the English rendering to R5). The seeded name, not the revision, decides,
  because R2's trigger bumps the revision on every grant change.
- **The retention defaults are O-23's rules.** Focus-loss events keep 13 months, which the deck's
  6 / 12 / 24 cannot express, so "13 months (default)" is a fourth option (DG-07). Answers are
  kept forever and disabled accounts are never anonymised. Production behaves as it does today
  until an admin changes a select (70 §6).
- **Removing answers keeps scores and comments.** The sweep replaces `attempt_answers.payload`
  with `{"removed": true}`; `auto_score`, `manual_score` and the grader's comment stay, so no
  result or average moves ("Scores are kept forever. This only deletes the answers.").
- **Plan & usage values are deploy configuration.** `PLAN_*` values in `fly.toml` are shown and not
  enforced (DG-55). A column the app cannot write would need a second write path for values that
  change once a year.
- **Transferring content requires a disabled source.** Moving a live teacher's drafts while they
  autosave would race the rule that a draft references only its owner's questions. Offboarding
  is disable, then transfer; moving one class under an active teacher is Change teacher.
- **The console reuses the teacher workspace's class operations.** Edit, rotate, archive, restore
  and adding members call `/teacher/classes/*`, which an Admin may call on any class through the
  wildcard and `scope.all`. Only the cross-teacher list, creating a class for a teacher and
  changing its teacher are `/admin/*` operations. Each rule has one implementation, and R2's
  isolation suite already covers them.
- **Assistant is shown, never assignable, until DG-04 is drawn.** Its card (0 people) and matrix
  column appear as the deck draws them, and its grants are editable under the subset rule (D2).
  Every place a role is picked leaves it out (Add user, the user sheet, bulk actions, import
  role values and New role's "Copy permissions from"), and the API refuses it there (`422
  ROLE_NOT_ASSIGNABLE`), as D14 says. Without class staff, an Assistant would be a teacher with
  fewer keys, which D14 rules out.
- **Two role reads, one key each.** `GET /admin/roles` (`people.roles.manage`) feeds the matrix;
  `GET /admin/roles/assignable` (`people.users.manage`) feeds the pickers and returns only roles
  the subset rule lets the caller assign, never Assistant, so no picker offers what the server
  would refuse.
- **Per-actor limits use R4's principal-keyed limiter.** Every limit this file gives "per actor"
  is registered in `PrincipalRateLimits()` and keyed by `ratelimit.PrincipalKey`, the limiter R4
  adds after `RequirePermission`; "per IP" and "per token" limits stay in `RateLimits()`, which
  runs before authentication.
- **The organization logo is served by the API, not by a signed URL.** Bytes carry a content-hash
  version for immutable caching and `Content-Disposition: attachment`. It is a PNG only: the
  browser that uploads draws an SVG to a PNG first (D-019, T-R5.28a). `img-src` gains the API
  origin.
- **Audit labels are resolved when read.** No label column joins the append-only log: a name
  frozen there could never be anonymised (D16). An entry about a deleted row shows its type only.
- **The audit tabs show counts, and the counts follow the search and the range.** The deck's
  search and date control are static, so it does not say what its badges count. They follow the
  contract's facet rule (`TestStatusFacets`): the current search and range, whichever tab is
  selected. `all` includes the entries only the All tab lists, so it can exceed the sum of the
  six families, as the deck draws (1,248 against 132). Decided 2026-10-03, with the deck
  re-import; `listAuditLog` had no facets before (T-R5.12, T-R5.26).
- **Lockout includes the actor.** A sign-in policy is refused when the user saving it, or every
  active Admin, would be left without a way in. Google counts only for accounts already linked in
  an allowed domain. The page asks the server for the impact before it offers Save.
- **Home is the last workspace used.** A built-in Admin lands on `/admin` the first time and
  afterwards on the workspace they last switched to (`preferences.workspace`); the owner teaches
  most days.
- **The front door's organization lines fall back to the build values.** Each line reads the
  Organization settings and falls back to R1's `VITE_ORG_*` values, so Forgot password keeps the
  front-desk phone between the deploy and the first save. The `VITE_ORG_*` build values stay.
  They are the Landing's contact source (R11), and the front door falls back to them when the
  API is unreachable.
- **`availability` stays its own module.** R1 left `organization` free to absorb it; nothing is
  gained by merging a read-only snapshot into a module with writes, logos and policy.

  - A worksheet (any part under `xl/worksheets/`, whatever its extension) above 8 MiB is

**As built (T-R5.15).** The migration is `00134_create_data_exports.sql` (renumbered if another R5 migration
merges first). Where it differs from the list above:

- The index is one `UNIQUE ((true)) WHERE status IN ('queued','running')`, not the plain
  `(created_at) WHERE …` index: it is the worker's queue and also what makes `409 EXPORT_IN_PROGRESS` a
  fact of the data when two Admins ask at once. `attempts smallint` counts the claims, and
  `data_exports_ready_has_file` also requires `bytes`.
- A claim lasts 30 minutes and a build is cut off after 25. An export still running past its lease is claimed
  again, up to three times, and then failed with `WORKER_INTERRUPTED`; a shutdown gives the claim back
  without spending the attempt. A worker whose lease was taken cannot complete, fail or release the row
  (every settle names the attempt it holds). Failure codes: `EXPORT_FAILED`, `EXPORT_TIMEOUT`,
  `STORAGE_UNAVAILABLE`, `WORKER_INTERRUPTED`; none carries a message.
- All files are read in one `REPEATABLE READ`, read-only transaction with a 20-minute statement timeout, so
  they describe one moment. Each file has an explicit column list in `exports/domain/files.go` (also the
  README's source, vi then en), and the snapshot refuses a query whose columns differ from it, so a new
  column on `users` or `attempts` never reaches a file unnoticed.
- `ready` becomes `expired` on read once `expires_at` has passed; the object and its key are removed by
  T-R5.16's housekeeping, which this task does not write. `expired` is therefore never stored here.
- The requester's own address is read from `users` in the transaction that marks the row `ready`, and the
  `data_export_ready` row is enqueued in it (dedupe key `data_export_ready:{id}`), so a rolled-back
  completion tells nobody.
- Without `IMPORT_S3_BUCKET` and the worker (`ImportProcessing`), the three operations answer `501 EXPORT_OFF`.
- A download is a signing, not a transfer: the browser fetches the object from storage, so the server never
  learns whether it finished. `downloads smallint` (0 to 3) counts the signings and `downloaded_at` keeps the
  first; each signing audits `data_export.downloaded`, and `DataExport.downloads` lets the exports page say
  how many are left (D-024).
- A worker killed mid-build leaves `export-{id}.zip` in `IMPORT_WORK_DIR`. When `RunOne` finds nothing to
  claim it lists the directory, asks the queue which of those exports are `running`, and removes the other
  archives (QC-D-2). The listing is taken first, so an archive created by a claim made after it is never
  taken for an orphan; names that are not `export-{uuid}.zip` are left alone.
- The hour is the export's, not the limiter's (D-021). `Postgres.Request` reads the actor's newest export that
  has not failed and is under an hour old, on `(requested_by, created_at DESC)`, in the transaction that
  inserts; if there is one the request is refused with `429 RATE_LIMITED` and `Retry-After`, the seconds until
  that row is an hour old (`domain.TooSoonError`). A failed export never blocks, and neither does a `409` or a
  `429`, which leave no row. Two requests at once by one actor are told apart by the active index (the second
  gets `409`). The registry entry for the operation is a 10-a-minute ceiling against hammering, and the
  contract declares the `429`.
- Audit actions `data_export.requested` and `data_export.downloaded` are in `modules/audit/domain` and both
  locale files, under All only. Schema: `20-data-model.md` §52, D-54.
- Measured: 50,000 attempts and 50,000 answers (1,000 students, 50 attempts each) stream into a 2.5 MiB ZIP
  in about a second; the live heap grew by 8 MiB (`GOGC=10` measurement in
  `server/tests/data_export_heap_test.go`, budget 24 MiB). Buffering the rows would have needed over 40 MiB.

**As built (T-R5.16, seven of the eight steps).** The box above stays open until the last step joins; each later one
is a `HousekeepingStep` in `core/housekeeping.go` and a command in the module that owns the rows. The set-password

- `jobs.Housekeep(ctx, logger, steps)` runs each `HousekeepingStep{Name, Batch}` in order. A step repeats its batch
  (500 rows or objects) while it comes back full, at most 20 rounds, under a one-minute budget of its own; a step
  that errors or runs out of time stops, is logged (`HOUSEKEEPING_STEP_FAILED`, or "left work for the next run") and
  does not stop the others. A log line carries the step's name, a count and, for a failure, its class (`timeout`,
  `canceled`, `database {SQLSTATE}`, `storage http {status}`, `network`, or `error`), never the error's text: the
  database and the storage client put keys, ids, the endpoint and the bucket into theirs. "Done" means a batch came
  back short, not that nothing is left (a named logo among the first 500 objects, or a second machine that found its
  rows already gone, ends a run early); the next run goes on. A step handles 10,000 rows or objects a run at most.
- The steps are assembled in `core/housekeeping.go`, the one place that knows every module, and handed to
  `PruneRefreshTokens` as a hook, which runs them after its own prune at start-up and on each 24-hour tick. No
  timer or wake is added, so an idle install still sleeps. A command a deployment lacks leaves its step out: the
  export step needs the import bucket, the logo step the media bucket. R7 adds its two steps to the same list.
- Each module owns a command that does one batch: `identity.PruneActivityDays` (the cutoff is the start of the
  local day 400 days back in `APP_TIMEZONE`, `domain.ActivityDaysKept`), `email.Outbox.Prune` (rows whose `sent_at`
  or `failed_at` is over `email.Retention`, oldest first; a pending row is never touched),
  `identity.PruneSetPasswordLinks`, `identity.PruneUserImports`, `exports.Expire` and `organization.SweepLogos`
  (T-R5.14's `identity.EraseExpiredImportSheets` is the seventh command; the avatar step will be the eighth step). Each is idempotent, so a second run removes nothing.
- `identity.PruneSetPasswordLinks` deletes the links whose `least(used_at, revoked_at, expires_at)` is over
  `domain.SetPasswordLinksKept` (30 days) old, the earliest first: a link ends at the first of the three, so one used
  or revoked inside its 24 hours goes 30 days after that, and one revoked after it had expired goes 30 days after
  it expired. `least` ignores a NULL, and `expires_at` is never NULL, so every link has an end. A link that can still
  be used has not ended and is never touched. A link that was never revoked is both a
  prune target and a target of `RevokeUnused`, so the batch locks its rows with `FOR UPDATE SKIP LOCKED`: it never
  waits for a row a claim, an issue or a disable holds, and so cannot form a cycle with them (without it, 250
  unrevoked eligible links per account deadlocked 14 and 22 times in 16 probes, and the victims included
  `RevokeUnused`, a 500 for the person; #679 QC-H-8). A locked row is passed over and the batch takes the
  next eligible one, so a batch is short only when the unlocked eligible rows run out; the skipped row waits for the
  next run. Nothing indexes the three columns, because the table holds the links of 30 days, a few
  thousand rows while the sweep keeps up; with a million eligible rows one batch still takes about half a second
  and a run under ten seconds. The cascade from `users` needs only `set_password_tokens_user_idx`. A pruned
  link's token answers as an unknown one does, which the `410 SET_PASSWORD_LINK_INVALID` body already does for a
  used, revoked or expired link, so nothing a person sees changes.
- `identity.PruneUserImports` deletes the jobs whose `completed_at` is over `domain.UserImportsKept` (30 days) old,
  the earliest first, and their rows with them (`user_import_rows.job_id` cascades). `completed_at` is set exactly
  when a job is `done` or `failed` (`user_import_jobs_completed_has_end`), so a `queued` or `running` job is never
  touched, however old. The accounts a job made, the classes it placed them in and the audit trail stay: the rows
  point at them and nothing points back. What goes is the names and addresses the rows keep as the file spelled
  them, and any sealed password still there, so a sheet whose 24-hour erasure has not run goes too. The batch
  counts jobs, not rows, and a job holds at most 2,000 rows, so a full batch of 500 is at most a million rows
  cascaded in one statement. QC measured the worst case at 2.86 s and 54 MB of WAL on a four-core machine, a twentieth
  of the step's minute (#701 QC-H-21); a centre that imports a few files a day does not approach it. The statement takes the
  job's lock and then its rows', the order `TakeSheet`, the worker's batch and `EraseExpiredSheets` take, and locks
  the job `FOR UPDATE SKIP LOCKED` so it never waits for a download in flight; a locked job is left for the next
  run. Nothing indexes `completed_at`, because the table holds the jobs of 30 days. The store is attached by
  `Application.SetUserImportRetention` from the identity wiring and not by `SetUserImports`, so a server whose
  import worker is off, which cannot create a job, still removes the names and addresses of the jobs it stored while
  it was on; `import_sheets`, which needs the sealer, runs only where the worker is configured. A removed job
  answers `404` on `getUserImport` as a missing one does, and a `requestId` it used would start a new job, which a
  dialog's request id, kept for the dialog's life, never does. An account anonymised under T-R5.17a keeps its old
  name and address in a row of a job less than 30 days old until the job goes. **Known limit (D-044, #701 QC-H-18,
  H-19, H-22):** the job is locked `SKIP LOCKED` and its rows are not, so the delete can wait for rows a class delete
  or a user delete holds (their `SET NULL` visits the same rows in another order) and, when one of those runs in the
  same moments, be chosen as a deadlock victim, `database 40P01` in the step's log; the next run goes on, and if the
  other action is the victim it fails and is repeated. The cycle exists between those two deletes without the prune.
  The cure, if it ever shows in a production log, is rows first in `(job_id, ordinal)` order with `SKIP LOCKED`, then
  the empty jobs, with a fixed row order in the two deletes.
- `exports.Expire` deletes the object first and marks the row second (`status = 'expired'`, `storage_key = NULL`,
  guarded by `status = 'ready' AND expires_at <= now()`). A crash between the two leaves a row past its time that
  the next run finishes; deleting a missing key succeeds. The read that reports a lapsed `ready` row as `expired`
  stays, so the page is right between runs.
- `organization.SweepLogos` lists the first `Limit` objects under `branding/` in key order (`storage.Client.List`,
  one `ListObjectsV2` page) and, for each one first written over 24 hours ago (`domain.LogoGrace`), reads the
  settings again and deletes it unless the light or dark logo names it. Listing first means a logo uploaded after
  the list is not in it; reading before each removal means a save that names an old orphan before that read keeps
  it, and nothing is read when no object is old enough. An upload of bytes already stored leaves the object as it
  was (`PutImmutable` sends `If-None-Match: *`), so re-uploading a replaced logo does not renew its 24 hours: if the
  sweep runs before the Admin saves, the save answers 400 and the Admin uploads again (#670 QC-H-1). The window
  that remains is the gap between the last read and the delete call, milliseconds: a save that names an orphan
  more than 24 hours old inside it leaves the settings naming a deleted object, and the logo cannot be read until
  the Admin uploads it again. The previous logo is removed at the first run after its replacement, whatever its age.
- An export object whose signed URL was handed out up to 60 seconds before `expires_at` answers `NoSuchKey` once the
  sweep has run. The outbox dedupe key of a pruned row is free again: the only producer today keys on the export id,
  so no message can repeat, but a producer whose key can come round after 30 days would send again
  (`email.Retention`).
- Tests pin the literal values, 400 days, 30 days and 24 hours with an object a minute either side of the edge and
  one exactly on it, and not the constants (#670 QC-H-2); a set-password link is seeded an hour past the edge and
  at least half a day inside it (13 hours for a used or revoked link, 36 for an expired
  one), once for each of the three ways it ends, and `SetPasswordLinks.Prune` is pinned to the
  microsecond (one older goes, one exactly on the edge and one newer stay). The rows of the earliest-first test are
  inserted newest first, so the heap order is not the age order (#679 QC-H-9, QC-H-10, QC-H-11); a test holds a row
  lock from another transaction and expects the prune to skip it and not wait (#679 QC-H-8). `PruneUserImports` is
  tested the same way: nine jobs in every state either side of 30 days (done and failed, a queued and a running one
  60 days old) with their rows, the account an import made untouched, the earliest first from jobs inserted newest
  first, the edge to the microsecond, and a held job skipped without waiting. `jobs.PruneRefreshTokensEvery` takes the tick as an
  argument so a test drives the second run; `PruneRefreshTokens` is it at `PruneInterval`. Each command is tested
  against seeded rows and a fake store, the repositories against Postgres, the storage listing against MinIO,
  `jobs/tests/housekeeping_test.go` for the batching, the budget, a failing step and the logged class, and
  `server/tests/housekeeping_flow_test.go` for the start-up run of the whole application (old rows and objects
  gone, rows inside their keeping and an object inside the grace untouched), for a storage endpoint that cannot
  be reached (the two storage steps fail, the others finish, and the log carries no key, id, endpoint or bucket)
  and for a server with the import worker off, which still removes an old import.
