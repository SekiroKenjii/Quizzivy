# R3 — Student console (v0.9.0)

The student half of the redesign. Every `/app` screen and the take-test engine are rebuilt to
`docs/design/deck/Quizzivy Student.dc.html`. This file also carries the contract half of R2's
expand steps: the legacy role enum goes, the ownership constraints are validated, and the
`/admin` path alias is removed. No teacher or admin screen changes. Where the deck is silent,
`docs/design/gaps.md` says what to build: DG-80 (engine frames), DG-81 (URLs) and DG-82 (badge,
bell, notification switches).

**Two versions (decided 2026-10-04).** v0.9.0 ships the student console, T-R3.4 to T-R3.14,
without T-R3.1, T-R3.2 and T-R3.3. Those three are R2's contract steps, and each needs v0.8.0
to have been in production for seven days. v0.8.0 was released on 2026-10-03, so they merge no
earlier than 2026-10-10 and ship as v0.9.1. Until then the code keeps `users.role`,
`app.user_role` and the sync trigger, the `NOT VALID` owner constraints with their fill
triggers, and the `/admin` alias.

**Migration numbers (2026-10-08).** `work/redesign-r4` merged 00080 to 00091 before these three
could merge, and production's `cmd/migrate` runs `goose.Up` without allowing missing versions,
so neither numbering works for a v0.9.1 from `develop`. Numbered from 00080, its files
collide with R4's versions where the branches meet, and goose refuses the duplicate in CI.
Numbered after 00091 and deployed first, it makes production refuse R4's 00080 to 00091 as
missing. Until Thuong decides otherwise, the three ship inside R4 as T-R4.49, numbered on
`work/redesign-r4`, and this file's release checklist runs inside v0.10.0's. A separate
v0.9.1 from `develop` would first renumber R4's merged migrations after its own
(`74-r4.md` T-R4.49). Where a document says "until v0.9.1", read "until T-R4.49 ships"; the
v0.9.1 checklist's docs sweep rewrites those lines.

Two constraints shape the file.

The first is risk. The engine is the highest-risk code in the product (70 §9 PR-3;
`30-risks.md` R-01, R-03, R-05, R-06), so it is rebuilt in four sub-PRs. Each sub-PR runs the
five canaries on its branch point and again on its last commit, together with
`pnpm test:unit tests/units/take-test tests/units/integrity tests/units/media`. The five
canaries are:

- `server/internal/modules/tests/application/tests/publish_snapshot_test.go`
- `web/tests/units/media/audio-player.test.tsx`
- `server/internal/modules/attempts/application/tests/events_test.go`
- `web/tests/units/api/client.refresh.test.ts`
- `web/tests/integration/router-chunks.test.ts`

The second is order. R3 and R4 are independent (70 §2 rule 4). If R4 ships before v0.9.1,
T-R3.1 to T-R3.3 move to R4 unchanged (74-r4.md T-R4.49). If it ships before v0.9.0, the
student bell and notification settings, which this file gates on R4's module, are built here
instead.

Branch `work/redesign-r3` is cut from `develop`. Feature branches are `feature/t-r3-<nn>-<slug>`.

**Deliverable:** the `/app` tree (Home, Classes with the Join dialog, Test intro, Result,
Settings) under a rebuilt `StudentLayout`. The engine is rebuilt in `FocusLayout` with split
passage and question panes, a footer number strip, a phone question sheet, flags, the focus
dialog, the copy-and-paste toast and the red timer. It keeps autosave and local drafts,
integrity capture, same-tick audio, section grouping and single-flight refresh. Learn, Grades,
Messages, This week, Practice and the bell stay absent until their modules ship. The R2
contract steps follow as v0.9.1.

**Exit criteria:**

- The five canaries pass untouched before and after every engine PR.

- The student console ships to production as `v0.9.0`.
- v0.9.1: `users.role` and `app.user_role` are gone, and no `NOT VALID` constraint is left in
  `app` outside the pinned list.

**Decisions taken in this file, worth a second look.**

- **The shell branches at 768px through a media query; pages use container queries.** The
  deck measures its root element with a ResizeObserver. The student shell *is* the viewport,
  so `useMediaQuery("(min-width: 768px)")` gives the same number and keeps
  `tests/support/viewport.ts` working. Thresholds inside a page (Home's two columns at 820) are
  CSS container queries on the shell's root, the container named `student`,
  which is exactly as wide as the viewport, as the deck's measured root is. They need no
  JavaScript. The delivery draft's `useContainerWidth` hook is not added.
- **The deck's Submit dialog replaces the full-page review screen.** The deck draws no review
  page. The dialog carries the same facts: answered, flagged, time left, and a "Go to" chip per
  unanswered question. The submit path is unchanged: it flushes, then submits, and stays
  idempotent against a racing auto-submit. Only the surface moves.
- **On phones, the save state appears only when a save has failed or the device is offline.**
  The deck shows "All answers saved" from 768 up and nothing on phones. A phone whose saves are
  failing must say so. A one-line strip under the header appears when a save has failed, or the
  device is offline, while an answer is unsaved, and goes away once the answer is saved. Where
  the assignment sets a limit on leaving, the strip is there from the start for the strike
  count, and only the failed or offline line comes and goes in it (T-R3.9a, As built). A save
  that is merely on its way draws nothing (amended in T-R3.9a's review): a strip for "Saving…"
  came and went on every answer, and either moved the paper under the student's thumb or cost a
  permanent empty row the deck does not draw. The strip is in the layout flow, so the paper
  moves once when it appears, which is acceptable for a state the student must not miss. From
  768 the header's save line is unchanged. The strip is listed for DG-80 sign-off.
- **An unknown question type renders a "reload" block, never a choice list.** Today the
  engine's `default` branch renders any unknown type as options and writes a `choice` answer.
  R6 adds three types, and a tab that loaded this engine earlier would mis-answer them. The
  block names the question, writes nothing, and offers to reload. R1's update prompt stays out
  of `FocusLayout`.
- **Keys are the deck's a–e plus the existing F for flag.** The deck binds a–e. The engine
  binds F to flag today, so a key for a sixth option would collide with it. Options after E
  are reached with Tab. Arrow keys and Esc work as the deck draws them.
- **"Larger text in tests" is stored locally until R4's `users.preferences` exists.** It lives
  in `localStorage['quizzivy.testText']`, read inside try/catch. R4 moves it to
  `preferences.largerTestText`, migrating the local value once (74-r4.md); after that the
  server value wins. This follows the theme rule in 70 §6.
- **The resume card's answered count applies the engine's rule in SQL.** "3 of 8 answered"
  must agree with the navigator's squares, which follow `take-test/answered.ts`: a fill-in
  counts only when every blank is filled. The student assignment list counts saved answers by
  the same rule, pinned by an integration test that runs the unit test's cases. An answer
  that exists only in the local draft is not counted.
- **Part tiles are summed on the client from sections.** The result gains `sections` and
  `ResultQuestion.sectionId`, both safe for students, and the page sums `earned` per part. A
  server-side `parts[]` would repeat the review-policy gate in a second place.
- **R3 has no attempt-level comment callout.** The deck's "Comment" callout has no model.
  `attempts.teacher_note` is the teacher's private note and must never reach a student.
  Per-answer grader comments stay on their review items. R6 handles the one case the deck
  draws, a single hand-graded essay.
- **The bottom tab bar shows only destinations that exist.** In v0.9.0 those are Home, Classes
  and Me. The deck's five tabs return one by one as R9 (Grades) and R10 (Learn) ship (70 §2
  rule 5). Nav items, the Messages button, the bell and the page controls read one availability
  map.
