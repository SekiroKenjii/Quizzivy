# R4 — Teacher workspace (v0.10.0)

The release that moves the teacher from the old `/admin` web tree to the deck's Teacher workspace
at `/teacher/*`. Every screen that exists today is rebuilt to `Quizzivy Teacher.dc.html`, the
backend gains what those screens draw and the server lacks, in-app notifications arrive for the
teacher and the student, a test can be imported from pasted text, the rich content editor
becomes the way a prompt and an explanation are written, and every legacy hashed join code is
rotated (D5).

R4 runs after R3 (v0.9.0, released 2026-10-04). It changes no permission rule and no API prefix.
It adds operations, each declaring an `x-permission` from `70-redesign-overview.md` §4.1 and each
added to R2's isolation suite in the PR that adds it, with an `x-resource` entry for every uuid
it takes in its path, query or body (T-R2.16).

If v0.9.1 has not shipped, T-R4.49 carries its T-R3.1–T-R3.3 unchanged.

Modules the deck draws that ship later stay invisible here: Calendar and Attendance (R8),
Messages and Shared with me (R7), Courses and Vocabulary (R10), Gradebook and Reports (R9), the
Admin console (R5). No nav item, palette entry, menu item or button points at them (70 §2 rule 5).

**Deliverable:** the Teacher workspace from the deck, for every module that exists today, served
at `/teacher/*` inside the new `TeacherLayout`, with the backend it needs: profile and
preferences, signed-in devices, in-app notifications in both consoles, assignment review options
and per-student overrides, a grading queue, question level and skill, media rename and replace,
class schedule and room, dashboard figures, a version diff, imports from pasted text and alt
text for a question's image. The builder, the bank's Question editor and the import review
write prompts with one content editor, in the deck's frame. Every legacy join code is rotated
at release, with an in-app notice to its teacher.

**Exit criteria:** every `/teacher/*` route matches the deck at 360, 768, 1024, 1280 and 1440, in
light and dark, with the sidebar expanded, collapsed and as a drawer (T-R4.51); the old teacher
tree is deleted and `router-chunks.test.ts` passes with its regexes updated, not weakened; no
active join code in production uses the legacy lookup; the pasted-text count fixture passes in
the Go and the web suite (T-R4.56, T-R4.57); the five canaries are green and untouched;
every CI step of 70 §8 is green in GitHub CI on every pull request, and once locally, in order,
at T-R4.52; released as `v0.10.0`, and Neon compute hours are measured for the week after (PR-7).

**Decisions taken in this file, worth a second look.**

- **Time-based in-app notifications are materialised when the reader asks, not by a timer.**
  "Closes in 1 hour", "due tomorrow", "opened" and "result ready after close" are inserted
  idempotently by `GET /me/summary` and `GET /me/notifications`, at most once per five minutes per
  user. An in-app item only matters while its reader is in the app, and a background timer would
  wake Neon at every threshold of every assignment (the #134/#143 lesson). R7 adds the email
  channel, and with it the first in-API notification scheduler.
- **Submission notifications are one row per assignment per 15-minute bucket, upserted at submit
  time.** That is the deck's "Grouped every 15 minutes" without a flush job.
- **Legacy join codes are rotated by an idempotent job at API start-up, not by a manual
  command.** The API holds `JOIN_CODE_KEY` on every start, while an operator holds it only for
  R2's rekey procedure, supplied to `cmd/maintenance` from the offline copy (`operations.md`); a
  human step at release is one that can be forgotten; the job takes an advisory lock, audits
  each rotation as System and does nothing on its second run.
- **Extend is two operations.** Extending the window for everyone changes the assignment
  (`teaching.assignments.write`); extending or reopening for chosen students is an accommodation
  (`teaching.attempts.intervene`, the "Reset, void or extend attempts" row). We keep one
  requirement per operation here by choice, so the dialog picks the operation. Both recompute
  the deadline of attempts already in progress, which today keep the deadline they started with.
- **The Grading page finishes an attempt when its last manual answer is scored** (DG-64). Today a
  teacher must press "Finish grading" on the attempt page; the deck releases on the last score.
  The attempt page keeps its explicit button for re-grading.
- **Bulk actions reuse single-item operations through `BulkActions`**, which already confirms and
  reports partial failure. The exception is password reset: the single operation is rate-limited
  to five a minute per address (R2's `RateLimits()` entry, per actor from T-R4.53), so a
  class-sized reset would 429. It gets one bulk operation, capped at 40 students, hashing at
  most two at a time inside the global argon2 semaphore. It stays in the API rather than the
  worker: forty hashes take about ten seconds and the screen waits for the printable sheet.
- **The unpublished-changes banner comes from a diff, not from `updated_at`.** Publishing and
  "Make default" both bump `tests.updated_at` through its trigger, and a bank edit to a question
  the draft uses bumps nothing on `tests`. The diff that DG-66 needs anyway compares the draft
  with the latest version.
- **Media replace creates a new immutable asset** and re-points bank questions and draft-owned
  groups only (DG-09), and only those owned by the asset's owner. Published versions, and other
  owners' rows (bound through `scope.all` today, copies from R7), keep the old asset, which
  leaves the library but keeps serving them. `publish_snapshot_test.go` is the proof.
- **In the teacher workspace, content lists show the caller's own rows for everyone, admins
  included** (DG-53, the question R2 left to R4). Tests, bank, media, imports and assignments
  list only what the caller owns; `scope.all` still reads and edits any teacher's content by id
  and powers the Admin console's cross-teacher views. Students and Classes keep `scope.all`
  lists until R5's Admin Classes and Users take them over (T-R4.54, 70 §4.1).
- **Test cards show skills derived from their questions**, not a `tests.skills` column. Chips that
  are computed cannot drift from the content; the deck's removable chips are prototype state.
- **Nothing a teacher can do today disappears because the deck does not draw it.** The test card
  keeps a "…" menu (Duplicate, Archive, Delete); Classes keeps an Archived filter (the deck's own
  archive dialog promises "you can restore it any time"); "View results" on a student opens
  today's results sheet until R9's Gradebook; the API reference stays a Settings section for
  `system.api_reference` holders until R5 moves it to the Admin console.
- **Display time zone is per user; the server stays UTC.** The profile's time zone drives every
  date the web formats and every date the teacher types. "Today" on the dashboard and the 23:59
  expiry of a join code use the actor's zone, defaulting to `Asia/Ho_Chi_Minh`.
- **A new join code expires at 23:59 local on its last day**, as the deck draws ("24 Oct 2026,
  23:59"), rather than at the minute it was made N days earlier. A code that dies mid-lesson is
  worse than one that lasts the day.
- **Duplicate assignment has no Title field.** Assignments are named by their test; there is no
  assignment title to copy. The dialog keeps "Assign to".
- **The workspace switcher ships as a static label.** Its popover and the `workspace.admin` gate
  are built, but the "Admin console" row appears with the console in R5 (DG-53, rule 5).
- **"Paste a test" is built here, as its own import source.** The 2026-10-03 export draws it and
  D1 builds what the deck draws, so it lands beside the Imports rebuild (T-R4.55–T-R4.57). The
  text arrives through its own JSON operation, not a second body on `uploadImportSource`: that
  route streams, so the contract validator would see neither the text nor its limit.
- **A pasted test is plain text, whatever the clipboard held.** The box is a textarea and only
  its text is stored, so the deck's "formatting kept" pill variants and stage lines would be
  false and do not ship (DG-12). Recognition never takes an answer from a mark,
  so nothing a teacher needs is lost.
- **The server learns the conventions the paste page teaches, for text sources only, with one
  exception.** The rules of T-R4.56 are gated on the text evidence version, so Word and PDF
  results do not move, except for the one-line answer key, which is read for every evidence
  version (#233, decided 2026-10-04): the local corpus run may report keys that are now read,
  and nothing else. `recognition.Version` becomes `rules-v3` and `PipelineVersion`
  `word-pipeline-v3`; a run queued under v2 at the deploy fails `PIPELINE_RETIRED` and its
  teacher retries, as at the PDF release.
- **The paste page counts with the server's grammar, not the deck's script.** One fixture,
  `api/testdata/pasted-text-counts.json`, is asserted by a Go recognition test and a web unit
  test, so "Found so far" cannot contradict the review. That is what lets Start processing stay
  disabled, as drawn, while the count finds no numbered question.
- **A paste holds at most 100,000 Unicode code points, counted after NFC normalisation.** The
  page normalises before it counts and sends, so the contract's `maxLength`, which counts the
  text as sent, agrees with the counter; intake normalises again and counts the same way. The
  deck counts UTF-16 units and its patterns miss decomposed Vietnamese.
- **Status filters are the segmented control with counts; the Imports history changes layout by
  its own width.** The 2026-10-03 export replaced the filter pills and the 940px scrolling
  table. The control keeps the product's semantics, a group of `aria-pressed` buttons and no
  tablist, because a filter has no tabpanel. The history turns from a grid into cards through a
  container query at 960px, not through the deck's viewport arithmetic.
- **The To review chips and the Ready card read "need action" for a pasted import too.** The
  count covers every blocking finding, not only missing answers, so the deck's "needs an
  answer" wording does not ship in either place (DG-14).

The 2026-10-04 export redrew the builder's editor pane and the review's "Question" field. The
seven decisions below are this file's defaults for it. Thuong has not confirmed them; each has a
line in the open items, and all but the first an entry in `docs/design/gaps.md`.

- **The content editor is the field, for every teacher.** The deck draws the rich editor as the
  builder's "Prompt" and "Explanation" and as the review's "Question". Most of it is on
  `develop` already (`web/src/components/shared/content/editor/`), behind
  `VITE_RICH_QUESTION_EDITOR`, which is off. R4 gives it the deck's frame and removes the flag
  (T-R4.63, T-R4.64). Options stay plain inputs, as drawn, so `VITE_RICH_OPTION_EDITOR` stays
  off.
- **The editing mode is the form the field is stored in (DG-110).** "Rich text" is stored
  content and "Markdown" is the stored Markdown string, as the contract has them today. A
  field opens in its own form, and a new field is rich text. The two conversions happen only
  on the teacher's "Switch to Markdown" or "Apply conversion". The prototype opens every
  question in Rich text and converts a field left in Markdown without asking; with autosave
  that would rewrite stored content nobody chose to change.
- **One `QuestionEditor`, built to the builder's drawing (DG-108).** The product renders the
  builder's editor pane and the bank's Question editor with one component, and the export
  redrew it in the builder only. The prompt, the explanation, the answer areas, the grading
  note and the question media are built once (T-R4.65, T-R4.66) and shown on both pages; each
  page keeps its own frame. "Match case" stays on a gap, because the model has it.
- **A prompt and an explanation hold no media in R4 (DG-109).** The contract's
  `QuestionContent` excludes media. Adding it runs through the publish snapshot, the student
  payload and the engine, three high-risk areas at once, and nothing draws the student side.
  R4 builds the toolbar without "Image" and "Audio" and refuses a pasted or dropped file;
  audio or an image is attached as question media. The backend and the two buttons go to R6.
- **The builder's type menu offers the five types the product stores.** "Matching" and the
  "Include “Not given”" switch need R6's types (DG-60, DG-113), and a control without a backend
  stays off the screen, as the import's do (DG-67).
- **Question media keeps the model's switches (DG-111).** "Students can pause" has no model and
  is not built. "Allow skipping ahead" and "Show transcript after submitting" stay, because a
  teacher sets them today. An image's alt text is new data: one nullable column on the
  question, frozen at publish (T-R4.62). The limits are DG-63's on every screen.
- **A pasted image is left out and counted; it no longer refuses the paste (DG-115).** The deck's
  "Preview content after pasting" says how many images were left out. Today the converter
  refuses any paste that holds an image, and spec §7.1 says to reject it as one paste. T-R4.63
  changes that one case and keeps every other refusal; T-R4.50 changes the spec line.

- **T-R4.1a: how a row opens.** The first data cell is wrapped in a `Link` (`rowHref`) or a

- **T-R4.3a: `useIdlePolling(ms: number, enabled = true): number | false`** is a query's
  `refetchInterval`: `ms` while `enabled`, the document is visible and the user is active, else
  `false`. It is called on the line above `useQuery`, and `refetchIntervalInBackground: false`
  stays.
- **T-R4.3a: activity is a `pointerdown`, `pointermove`, `keydown`, `wheel` or `touchstart` on
  `window` within `IDLE_AFTER_MS` (600 000).** One store for every consumer: the first attaches
  one set of listeners and one timer, the last removes them, an input only writes a timestamp,
  and a consumer re-renders when idleness or visibility flips, never on a mouse move. The
  listeners are passive and on the capture phase, so a handler that stops propagation (a row
  menu does) cannot hide an input.
- **T-R4.3a: mounting counts as activity through the store's first consumer.** The ten minutes
  start when the store attaches. A consumer that joins an idle store answers `false` until an
  input or a return to the tab, so a mount nobody caused cannot wake every poll; a disabled
  consumer attaches nothing.
- **T-R4.3a: `useRefetchOnResume(refetch: () => unknown, enabled = true): void` refetches at
  once when the user comes back:** once at the first input after idleness and once when a hidden
  document becomes visible, never on mount, because `enabled` changed, or on an input from a user
  who never left. The query client has `refetchOnWindowFocus: false`, so without it a monitor
  watched without input would show data up to ten minutes old for one more interval after the
  teacher's first mouse move. TanStack restarts the interval from that refetch.
- **T-R4.3a: becoming visible counts as activity.** A tab that comes back, after however long,
  refetches once and polls for another ten minutes; the first input after it does not refetch.
  Somebody brought the tab back, and without this a teacher who returns with the keyboard or on
  a tablet would read a roster that froze at the moment of return.
- **T-R4.3a: the old detail page's `monitor.polling` sentence is untrue for an idle teacher.**

- **T-R4.3a: the content width is the registered element's border-box width minus its computed

  hysteresis is needed. The padding is read at every measure, because it changes at 768.
- **T-R4.3a: `contentWidth.ts` exports three things.** `registerContentElement(element | null)`
