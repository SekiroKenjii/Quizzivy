# R2 — Access (v0.8.0)

R2 turns a one-admin application into a multi-teacher one and changes no
screen. It does six things:

- stores the permission catalogue and the built-in roles as data
  (`70-redesign-overview.md` §4.1);
- enforces one declared permission on every operation, driven by the contract;
- gives every class, test, question, question group and media asset an owner,
  and scopes every teacher read and write by that owner;
- moves the teaching operations from `/admin/*` to `/teacher/*`;
- stores new join codes encrypted, found through a keyed lookup;
- raises the join and sign-in rate limits so a whole class can sign in from
  one school address.

It ships alone (70 §2 rule 3), so any regression between v0.7.0 and v0.8.0 is
an access bug. At release, production has one staff account and its students.
The owner's `role='admin'` maps to the built-in Admin role; students map to the
built-in Student role. No UI can create a second teacher until R5's Users page
(rule 2). Until then, three things prove the multi-teacher behaviour instead of
production traffic: the seeded second teacher, the two-teacher isolation suite
and the escalation tests.

The Assistant role exists with the deck's grants. It owns nothing and is
attached to no class until DG-04 is drawn, so an assistant reaches the teacher
workspace and finds it empty. No role picker offers the role yet (D14).

Every change here is the expand half. The contract half belongs to R3, or to
whichever release ships next (70 §2 rule 4). That release:

- validates the `NOT NULL … NOT VALID` constraints and drops the fill triggers;
- drops `users.role`, its sync trigger, `users_role_active_idx` and
  `app.user_role`;
- removes the legacy `/admin` alias;
- stops issuing the legacy `role` claim.

Nothing in R2 may rely on those objects being gone, and nothing R2 writes may
rely on them staying.

Order of work: T-R2.1 to T-R2.8 build the permission model and the path move.
T-R2.9 to T-R2.13 add ownership, scoping and the guards that are not
permissions. T-R2.14 and T-R2.15 cover join codes and rate limits. T-R2.16 to
T-R2.19 prove the release, align the web and update the docs. The join-code
work (T-R2.14a) and the ownership migrations (T-R2.9) do not depend on each
other and can run beside T-R2.3 to T-R2.8.

**Deliverable:**

- **Permissions.** Roles and the permission catalogue are data. Every one of
  the 104 operations (103 today plus `getJoinCode`) declares `x-permission`,
  or is open. `httpx.RequirePermission` replaces the `/admin/` prefix gate.
  A short per-user principal cache supplies each request's role, permissions,
  `disabled_at` and session epoch.
- **Ownership.** Classes, tests, questions, question groups and media assets
  have owners. Repositories filter by `access.Scope`, and another teacher's
  ids answer 404.
- **Paths.** Teaching operations live under `/teacher/*`. An outer alias
  serves the old paths for one release, and every rate-limit key has moved.
- **Join codes.** New codes are stored with AES-256-GCM and found by a keyed
  HMAC. Legacy codes still redeem. The key can be rotated, and the procedure
  is documented.
- **Guards that are not permissions.** Strict student targets, the subset
  rule, the last Admin, and foreign-key refusals answered as 409.
- **Rate limits.** Join and sign-in limits are sized for a classroom.
- **Web.** Guards read permissions instead of a role, with no visual change.

**Exit criteria:**

- **Contract checks hold.**
  - The startup assertion, `permissions_test.go` and the web contract test
    agree: every operation declares a permission, the open operations declare
    none, and every key is in the catalogue.
  - `RequireRole` is gone.
- **Isolation and escalation tests are green.**
  - The isolation suite shows teacher B getting 404 for every `/teacher/*`
    operation aimed at teacher A's data, and never seeing A's rows in a list;
    student B gets the same on `/app/*`.
  - The escalation tests are green, including an Admin with "Take tests"
    turned on as the target.
- **Migrations are safe to roll out.**
  - The old-binary insert test is green.
  - Migrations pass up, down, up.
  - The Neon rehearsal on a production branch is recorded.
- **The rest of CI and the live join test pass.**
  - Every CI step passes locally, in order (70 §8).
  - The live test in which thirty students join from one address is green.
- **v0.8.0 runs in production with nothing visibly changed.**
  - The owner's daily work is unchanged, and so is a student's.
  - A legacy join code redeems.
  - Tabs still open on v0.7.0 keep working through the alias.

**Decisions taken in this file, worth a second look.**

- **`x-permission` is a key, a pseudo-key, or a list meaning "any of".**
  70 §4.2 gives each operation one key. Three families of operations need two:
  - Question and question-group writes serve both the bank
    (`content.questions.write`) and the test builder (`content.tests.write`).
  - The attempt-review reads serve both graders and teachers who intervene.

  The middleware accepts any listed key. When the body decides which key
  applies (a bank destination or a section), the handler narrows the check.
  Handlers already own rules the schema cannot express. The alternative,
  `workspace.teacher` on those writes, would let a role that only takes
  attendance edit the bank. 70 §4.2 states this form and names the families
  that use a list.
- **Reads declare `workspace.teacher`; matrix rows gate actions and student
  data.** The deck's matrix has no "view tests" row. Listing tests, questions,
  groups, media, classes and assignments, and opening the dashboard, needs any
  teacher key. Student data needs `people.students.read` or a teaching key.
  Ownership scoping, not the permission, keeps another teacher's rows out.
- **`scope.all` lifts every owner filter, in lists as well as by id.** The
  owner owns everything today. Filtering their Students list to "my classes or
  created by me" would hide students who belong to no class and have a NULL
  `created_by`, and hiding them is a visible change. R4 decides the Admin's
  teacher-workspace lists (DG-53). The proposal for 70 §4.1: `scope.all`
  keeps reads and edits by id and the Admin console's cross-teacher views,
  while content lists in the teacher workspace (tests, bank, media, imports,
  assignments) show the caller's own rows, admins included; Students and
  Classes keep `scope.all` lists until R5's Admin Classes and Users take them
  over. Either answer is the `Scope` a list query receives, so R2 builds
  nothing that R4 must undo.
- **The subset rule ignores `learning.take_tests`.** 70 §4.3 requires the
  target's permissions to be a subset of the actor's. Read literally, no Admin
  could disable a student, because the Admin wildcard lacks "Take tests" unless
  it is turned on (DG-51). That key gives no power over another person, so the
  rule compares the target's set without it. Admin targets stay protected,
  because the wildcard holds every other key. 70 §4.3 states the rule this
  way; Thuong confirms this reading of D13 (open items).
- **One database view, `app.student_like_roles`, is the strict student
  predicate.** It holds the built-in Student role, plus any custom role
  (`builtin_key IS NULL`) whose grants are a subset of
  `{learning.take_tests}`. Every repository and `core/maintenance` use it. The
  Admin row stores only its "Take tests" cell, so a definition based only on
  grants would classify the Admin as a student. That is the takeover the
  critic found; excluding built-in roles by key closes it. There is one
  definition and one test.
- **`deleteStudent` becomes `DELETE /admin/users/{id}` (`deleteUser`,
  `people.users.manage`) and stays student-only in R2.** Deleting an account
  is a People-row action, not a teaching one. Under `/teacher/*` it would
  break the path-tree rule (T-R2.7). R5 keeps it student-only, with no
  console control: offboarding is disable, then transfer.
- **A teacher resets or re-addresses only a student no one else reaches.** A
  student is visible to every teacher who reaches them (T-R2.12d), so without
  this rule teacher B could reset a student shared with teacher A, receive the
  temporary password and sign in as the student. Changing the student's
  email to an address B controls does the same through Google sign-in, which
  links by email. `resetStudentPassword`, and `updateStudent` with a new
  `email`, therefore require that no one else reaches the student:
  - every class of theirs, archived ones included, is one the actor teaches;
  - no other account created them;
  - no other account's assignment targets them individually;
  - with no class, the actor created them.

  Anything else answers `403 STUDENT_SHARED`, and the write goes to a holder
  of `people.users.manage` (T-R2.13). In R2 the only staff account is the
  Admin, which holds that key, so nothing visible changes.
- **`updateStudent` with `disabled` also needs `people.users.manage`.** The
  operation itself declares `people.students.create`. "Add and disable users"
  is Admin-only in the matrix, and the deck's teacher Students page has no
  Disable.
- **A test draft's references keep one owner.** A draft may reference only
  bank questions owned by the test's owner. The owner is checked after
  `questions.LockForDraftUse`, which stays the lock the canary pins. A
  duplicate or a restored draft belongs to the source test's owner. The cost
  in R2: an Admin editing another teacher's draft can pick only that teacher's
  questions. Creating a new question from the builder inside that draft fails
  too: the question belongs to the Admin, so the draft refuses it, and it stays
  in the Admin's own bank. R7's copy-on-add and `forTestId` remove both limits. Media works differently:
  assets are immutable, so a reference only requires that the actor can read
  the asset.
- **Principals are cached for 10 seconds.** A write on the same machine
  forgets the entry at once. A disable or a matrix edit therefore applies on
  the next request on that machine, and within 10 seconds on any other. This
  keeps autosave and the monitor's polling from adding a query per request,
  which would keep Neon awake (PR-7).
- **In R2 the session epoch moves only on disable and on a staff password
  reset.** Those are the only R2 operations that must end live sessions at
  once. R5's "Sign out everywhere" and role changes will also move it.
- **The last-admin guard is a trigger now, although no R2 operation can reach
  it.** `users_last_admin` serialises on the Admin role row and refuses to
  leave zero active Admins, whatever the path: R5's commands, a bulk action or
  a hand-written `UPDATE`. Its function is `SECURITY DEFINER`, because the
  `FOR NO KEY UPDATE` it takes needs UPDATE privilege on `app.roles`, which
  T-R2.1 revokes from the app role. The `409 LAST_ADMIN` code joins the contract with
  the first operation that can return it (R5).
- **The API can read a full join code in R2; the screen that shows it comes in
  R4.**
  - `GET /teacher/classes/{id}/join-code` returns `{code, legacy}`.
  - A legacy row answers `code: null, legacy: true`, the explicit state the
    critic asked for.
  - R4 is then only UI plus the rotation of legacy codes (D5).
  - The key id is a 16-bit HKDF fingerprint of the key rather than a number an
    operator picks, so a rotation cannot reuse an id by mistake.
- **Built-in role names and descriptions are seeded in Vietnamese**: Quản trị
  viên, Giáo viên, Trợ giảng, Học viên. They are data in the organisation's
  language and editable later (D2). R5 renders a built-in role whose stored
  name is still the seeded one from `role.builtin.<key>`, so an English matrix
  reads "Teacher". Thuong reviews the four rows in T-R2.1 (D11).
- **The rate-limit numbers in T-R2.15 are proposals, built as corrected in
  T-R2.15 (Thuong confirms).**
  - 120 requests a minute and 600 an hour per address for join preview,
    join, Google sign-in and sign-in; 120 a minute and 1,200 an hour for
    refresh and logout.
  - 200 an hour per code; per email, 10 a minute from one address and 20 an
    hour overall.
  - No bucket per address and code. The first text proposed one at 10 a
    minute "so one device cannot hammer a code", but a class behind a
    school's shared address is one address with one code: its 11th student
    would have been refused, which contradicts this task's own classroom
    test. Repeating a valid code gains nothing, and the per-code bucket
    already bounds how often any code is tried.

  A class of 40 with three tries at each step fits inside a minute. Join
  preview and in-app join each tell a caller whether a code is valid, and
  each has its own 600-an-hour budget per address, so one address with a
  student account can test about 1,200 codes an hour; Google sign-in adds its
  own, but each try needs a fresh Google authorization. Against 32⁸ possible
  codes that is still negligible. Each keyed operation takes a body of at
  most 8 KiB, and a body key is decoded as the handler decodes it, so no body
  shape skips the per-email or per-code bucket.

    autosave, event flush and plays take these ids, not bank ids.
  - **A map's keys.** `saveAnswers`' `answers` is keyed by the version
    question's id. The contract now says so with `propertyNames: Uuid`,
    and `+` in a pointer stands for every key. The request validator does
    not enforce `propertyNames`, so a key that is not a uuid is still a 500
    (#220).
  - **A polymorphic id.** A section unit's `id` names a question or a group,
    as its `kind` says. It is declared as a question. The flow checks the
    group branch separately: B's draft naming A's section group or A's bank
    group answers as a missing group does, and naming its own group
    succeeds.
  - **The oracle.** Every slot whose kind is not `none` is sent with A's id
    and with a random uuid. The two answers must be equal: the status and
    the whole body, with uuids and timestamps masked and `requestId`
    dropped. A random id must not succeed unless the table excuses the slot
    with a written reason. The slot is then sent with B's own id, which must
    answer differently; that proves the case reaches the check. The table
    exempts a slot from this third send only with a written reason
    (`blind`). Twenty operations that change or consume their resource get
    a fresh one for each send: the deletes, the group archive, the attempt
    reset and void, the password reset, the member removal, the version
    operations, the test and group edits and copies, the import cancel and
    the review save.
  - **Excused slots**, where a random id may succeed:
    - `listTestVersions`, `listAssignments?classId`, `listStudents?classId`
      and `listClassMembers`: a filter or parent that does not exist lists
      nothing. B's own id lists B's rows.
    - `tagQuestions` tags only the questions the caller reaches. B's own
      question is tagged.
    - `removeClassMember`: removing someone who is not a member succeeds.
    - `saveAnswers` and `flushEvents`: an event naming a question outside
      the attempt's paper is kept without it, and an answer to one is
      dropped.
    - `saveWordImportReview` stores asset references unchecked.
  - **Blind slots**, where B's own id answers as a missing one does:
    `removeClassMember`'s user, the two event questions, the answer key and
    the five review assets (an option holds one text paragraph, so an asset
    there is refused whatever it names). What proves these is the
    cross-reference scan and the commit check below.
  - **Checks beyond the table.**
    - Committing a review that holds A's image answers as a missing image
      does, and one holding B's own image commits. The commit resolves media
      in the import owner's scope.
    - The beacon (a text body with `beaconToken`), sent by an anonymous
      client to A's attempt, answers as a missing attempt does.
    - **The cross-reference scan.** No row in schema `app` holds both an id
      of A's and one of B's. B's ids are the seeded ones plus every
      resource a fresh helper made. The exception is `word_import_drafts`,
      where a save stores what the teacher typed. `audit_log` is included.
    - **Rows naming A's ids.** Every row in schema `app` that names one of
      A's ids, outside `word_import_drafts`, is identical before and after
      the table. So is the digest of A's owned rows.
    - **The views.** Each list, `getDashboard`, the student's `listMy*`
      views and the shared student's record are read before and after A
      seeds. A list with an optional id filter is read both unfiltered and
      filtered to B's own id. They must be byte-identical once the signed
      URLs' query strings are stripped.
  - **Seeding.**
    - Each teacher's bank question carries a tag, so a facet that counted
      another teacher's rows would change.
    - A reviewed import is seeded in SQL (a succeeded run and a draft),
      because processing runs in the worker.
    - The student side is a second student with an in-progress attempt on a
      listening test, so the attempt has a group recording.
    - A third student of B's joins A's class by its code once A has seeded,
      then sits and submits A's assignment. B's record of that shared
      student, and the stats in B's lists, must still show only B's
      classes and work.
    - The import quotas are raised for the fresh imports. The test cancels
      every import the two teachers left open, because the global quota
      counts every open import in the database.
    - `/me/*` has no operations yet. The table must name R4's when they
      arrive.
  - **Result.** No leak was found. The run takes about 10 to 17 seconds
    locally.

## Open items

- **Classroom size.** The per-code budget of 200 an hour assumes classes of
  up to 40 and three tries per step (T-R2.15). Default: build as proposed. If
  Thuong runs larger sessions, such as a whole year group in a hall, raise the
  per-code bucket only.
- **Enforcing `mustChangePassword` on the server.** Today only the SPA
  redirects a user with a temporary password; the API serves them in full.
  `RequirePermission` could refuse every operation but `self` until the
  password changes. That is not in R2, because it would change behaviour for
  sessions already in flight. Default: not enforced in R2. R5 takes the
  decision with its set-password link (D15, DG-05) and proposes
  `403 PASSWORD_CHANGE_REQUIRED` (O-R5.4).
- **The two amendments to 70 §4:** the any-of form of `x-permission` (§4.2),
  and the subset rule ignoring "Take tests" (§4.3, D13). 70 carries both.
  Default: build as written here. Thuong confirms the D13 reading.
- **The Admin's lists in the teacher workspace.** They show everything in R2
  (`scope.all`), which is no change while the owner owns everything. R4
  decides the default (DG-53). The proposal: content lists show the caller's
  own rows, admins included; Students and Classes keep `scope.all` until
  R5.
- **Resetting or re-addressing a shared student.** Default, as built in
  T-R2.13: a teacher's reset, or email change, is refused with `403
  STUDENT_SHARED` unless no one else reaches the student. That means every
  class is the actor's, no other creator, no other account's individual
  target, and, with no class, the actor created them. A holder of
  `people.users.manage` is exempt. Three points go beyond the plan's first
  text, which looked only at memberships and only at resets:
  - the email change, which Google sign-in's link-by-email turns into a
    takeover;
  - the created-by and individual-target arms of reach;
  - archived classes counting as memberships.

  It is the safer reading, because the alternative lets one teacher take
  over a student another teacher shares, and from R7 read their direct
  messages (D17). Thuong confirmed the stricter reading on 2026-09-28.
- **Self-join by an Admin who takes tests.** From R5 an Admin can turn on
  "Take tests" (DG-51). The server then accepts that Admin's `joinClass`,
  because the operation needs only `learning.take_tests`, while rosters,
  resets and assignment targets never treat the Admin as a student. The web
  keeps v0.7.0's rule (T-R2.17): JoinPage tells that Admin joining is for
  students, although the student app now opens for them and links to
  `/join`. Default: unchanged in R2, where no Admin holds the key. R5
  decides whether such an Admin may self-join, then aligns the server's
  enrol path, JoinPage and the student app's join links with the answer.
