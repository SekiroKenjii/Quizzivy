# R7 — Collaboration (v0.13.0)

Three capabilities the deck draws and the backend lacks. **Sharing** (D4): an owner shares a test
or a question set with other teachers, each recipient getting **Can use** or **Can edit**, and a
recipient finds it under "Shared with me". **Messages** (D17): one announcement channel per class
and direct messages between a teacher and a student. **Email** (D9): the notification rules R4
built in-app gain their email channel, with the first in-API notification scheduler.

Screens are compared with `docs/design/deck/Quizzivy Teacher.dc.html` (the share dialog `sh.*`,
Shared with me `shr.*`, `r.messages`, `r.settings` › Notifications) and
`Quizzivy Student.dc.html` (`messages`, the Classes card's message button, Settings ›
Notifications). The deck draws sharing for tests only and draws no question set, so DG-90's
interim answer governs the question-set surfaces. DG-91 settles the messaging questions, and
DG-08 the admin boundary on direct messages.

**Deliverable:**

- Tests and question sets are shared per recipient as Can use or Can edit. Every shared read model
  carries the caller's `access` and its `owner`.
- A Can-use recipient gets a read-only builder and question editor. A Can-edit recipient co-edits
  under the stale-write guard.
- An edit to a bank question the owner uses elsewhere forks it (copy-on-write).
- Make a copy, Remove from my list and Stop sharing work as the deck draws them. Revoking keeps
  assignments working.
- Class announcement channels and teacher–student direct messages. Direct messages are readable by
  their two participants only. Staff can attach files, which are sniffed like media.
- Unread counts, read pointers, "Seen by", and polling that stops when the user is idle.
- Email for flagged attempts, extensions, shares, grouped submissions, new messages, due-soon
  reminders, closing assignments, released results and the weekly summary. Each email follows the
  recipient's switches.
- Hard bounces and complaints reported by Resend stop further mail to that address (R5's O-R5.2).

**Exit criteria:**

- The isolation suite covers every new operation under no grant, use, edit and a revoked grant.
- A copy-on-write test shows that test B's draft is untouched when an edit grantee changes a
  question in test A.
- Live E2E runs the share round trip and the message round trip.
- E2E 9 walks `/app/messages/*`.
- The five canaries and `TestLockForDraftUseSerialisesAgainstDelete` pass untouched.
- Every new screen matches the deck at 360, 768, 1024, 1280 and 1440, in light and dark.
- Neon compute hours are measured for the week after the release (PR-7).
- The release ships to production as `v0.13.0`.

**Decisions taken in this file, worth a second look.**

- **A question set is a named, ordered selection of the owner's standalone bank questions**
  (DG-90, interim). It holds references, not copies, and it is made from the bank's bulk bar. Tags
  and saved filters were rejected as the definition, because a recipient would silently gain
  whatever the owner tags later. Passage and cloze groups are left out: in a draft they are
  test-owned copies, so they travel with the tests that use them. Adding questions to a set is the
  owner's job. An edit grantee changes the set's questions and removes items, but does not add
  them (open item).
- **`content_shares` stores no owner.** The owner is always the resource's current owner, reached
  through a typed nullable foreign key per kind (`test_id`, `question_set_id`) plus a `kind`
  column and CHECKs. A grant therefore cannot disagree with its resource. R5's ownership transfer
  moves grants without a cascade. R10 widens the table with `word_list_id` and `course_id`, each a
  plain `ON DELETE CASCADE` FK with no owner column, by replacing the three CHECKs
  (`content_shares_kind_check`, `content_shares_one_resource`, `content_shares_kind_matches`). A
  polymorphic `resource_id` was rejected, following the house preference for real foreign keys
  (D-05, D-17).
- **Grantees see what the owner sees: the draft and every version.** Can use is read-only. Make a
  copy copies the current draft. Hiding unpublished work from Can-use recipients would give the
  builder a second data source, and the owner already chose to share the test.
- **A draft only references questions its test's owner owns.** R2 enforces this (T-R2.12a), and
  R7 adds the "copy-on-add" R2 left for it. When an edit grantee creates a question in a shared
  test, adds one from their own bank, or copies in a group, the result lands in the owner's bank,
  with `created_by` recording the grantee. So the owner can always manage
  every question in their own drafts, and `LockForDraftUse` stays sufficient. The rule applies to
  anyone who is not the test's owner, admins included.
- **Copy-on-write is decided per edit, not per share.** A non-owner who edits a bank question in
  the context of a test or set they can edit gets a fork when anything else references the
  question: another draft, or another set. The fork belongs to the question's owner and is
  created by the editor. Only that context is re-pointed to it, and the decision is taken under
  the question's row lock. The owner's own edits never fork, and change every draft that uses the
  question, as today. Without the fork, an edit grant on test A would silently change test B,
  which was never shared.
- **Revoking deletes the grant row and nothing else.** A grantee's assignment references an
  immutable version, and every read that starts from an assignment (monitor, grading, results,
  export) reaches that version through the assignment's scope, never through a share. The
  grantee's students' results stay in the grantee's classes, as the deck's footnote promises.
- **A disabled owner's grants stay valid.** Recipients keep teaching with what they were given.
  Shared with me marks the owner "Account disabled", and R5's transfer is how the content changes
  hands.
- **Share notifications have no recipient switch.** The deck draws none, and DG-90 says the
  message arrives in-app and by email. The sharer's "Send a notification" decides.
- **A direct message is addressed by its counterpart, and its conversation row is created by the
  first post.** Routes and the contract speak of `/students/{id}` and `/teachers/{id}`, so the
  Students page, class detail and the student's class card can open a thread without a create
  step. Class channels are listed for every class in scope, whether or not anyone has posted yet.
- **`scope.all` never opens a direct message (D17, DG-08).** Direct messages are visible to their
  two participants only. Class channels are class content and follow class scope, admins
  included. Admins get counts in the data export, never contents. A password reset cannot open
  them either: a teacher's reset, single or bulk, is allowed only when every active membership
  of the student is in a class the actor teaches (or, with no memberships, the actor created
  them), and anything else answers 403 `STUDENT_SHARED` and goes to a holder of
  `people.users.manage` in the Admin console (T-R2.13, T-R4.20). Without that, teacher B could
  reset a student shared with teacher A and read the A↔student thread.
- **Messages are append-only for the app role.** Nothing can edit or delete a message, as with
  `attempt_events` and `audit_log`: the log of teacher–student contact protects both sides, and
  most students are minors. Deletion happens in one place only, when D16's anonymisation removes
  an account's direct conversations under the maintenance role.
- **Message posts, reads and attachment uploads are not audited.** The append-only `messages`
  table is the record, readable only by its participants (D17). An audit row, even with ids only,
  would show `system.audit.read` holders who wrote to whom and when, and would outlive the direct
  conversations D16 anonymisation deletes, because `audit_log` is append-only.
- **Attempt-event cards are computed when a staff member reads a thread; they are not stored as
  messages.** A staff member's direct thread shows the student's flagged attempts on assignments
  that staff member can read, from 24 hours before the thread began. The student projection is a
  separate Go type without the field (DG-91: teacher-only). Storing them would create threads out
  of flags and repeat the flagged notification in two places.
- **Students cannot attach files.** The student deck draws no paperclip. Staff attach PDF, PNG,
  JPEG, MP3 or M4A up to 20 MiB, sniffed by content as §11.1 does for media and served as a
  download through a five-minute signed URL. WebP is refused: every image attachment must pass
  `image.DecodeConfig`'s dimension cap, the standard library has no WebP decoder, and a new
  dependency for one format is not worth it.
- **Polling, not a push channel.** An open thread polls every 10 seconds through R4's
  `useIdlePolling`, which stops after ten idle minutes. Unread counts ride on the 60-second
  summaries R4 already polls. There is no ETag cache: R2's principal cache removes the per-request
  permission read, and an active poll only runs while someone is using the app. The compute hours
  are measured after release (PR-7). A push channel over SSE would first need `LISTEN/NOTIFY`
  across machines and heartbeats under Cloudflare's idle timeout.
- **An email never carries a message body.** It names the sender and the class and links to the
  thread, so D17's contents stay inside the app. A new-message email waits ten minutes, is sent
  only if the thread is still unread, and goes at most once per thread per 30 minutes. A share
  email carries the sharer's optional message, as DG-90 says.
- **One scheduler in the API process wakes only when an email is due, or after six hours.** It
  computes the next due time from the database and sleeps until then. Assignment writes nudge it,
  and an advisory lock plus outbox dedupe keys make it safe on two machines. A fixed-interval
  ticker would keep Neon awake (#134, #143). R4's in-app due items keep being created when the
  reader asks; the scheduler handles email and the weekly in-app summary only.
- **Student switches cover both channels (DG-82), so students start receiving email in R7.** Test
  due soon, Result ready and Messages from teachers were in-app only in R4, and in R7 they email
  too. The release note says so. A per-event kill switch, `NOTIFY_EMAIL_EVENTS`, turns off any
  event's email without a code change if volume or bounces demand it (open item on the Resend
  plan).
- **Bounces and complaints get a signed webhook and a suppression list now, not later.** R5
  deferred them "until R7 raises email volume" (O-R5.2), and R7 is where students' typed
  addresses start receiving mail. Repeated sends to dead addresses cost the domain its
  reputation. The webhook is a new public operation, so it is rate-limited and leak-reviewed in
  its own PR. It accepts only Resend's signed deliveries and answers nothing a caller could use.

## Open items

- **O-R7.1 — Resend plan and volume.** Due-soon emails go to each student at 24 hours and 1 hour
  before close, so a class of 30 costs about 60 emails per assignment, before results, messages
  and teacher emails. R5's `EMAIL_DAILY_LIMIT` (100, the free tier's cap per O-R5.1) defers the
  excess to the next day, where `Prepare` drops what went stale. The mail is not lost, but it
  arrives late. Default: measure on the Neon branch (release checklist). Ship with every event on
  if the plan covers it; otherwise ship with the student's 1-hour reminder off through
  `NOTIFY_EMAIL_EVENTS`.
- **O-R7.2 — Message retention.** Admin › Data & privacy has no messages setting. Default: keep
  messages while both accounts exist, and delete an account's direct conversations when D16
  anonymises it. A retention choice needs a design row first, which T-R7.25 proposes in
  `gaps.md`.
- **O-R7.3 — Showing a suppressed address.** T-R7.15 stops mail to an address that bounced or
  complained, but no screen shows it. The Admin deck's user sheet draws no email status, and a
  teacher cannot tell that a student's reminders no longer arrive. Default: the suppression is
  logged, and an admin removes it by changing the user's email. A design row is needed for the
  user sheet, which T-R7.25 proposes in `gaps.md`.
- **O-R7.4 — Edit grantees adding questions to a set.** R7 lets an edit grantee change and remove
  a set's questions, but not add them (decision above). Default: owner adds. DG-90 is asked.
- **O-R7.5 — Class staff in Messages.** Assistants attach per class (D14, DG-04), but that link
  is not drawn, so a class's staff in R7 is its teacher. When class staff ships, it joins channel
  posting and DM eligibility.
- **O-R7.6 — Auditing message activity.** The review allowed either no audit for posts or audit
  rows with ids only. Default: no audit row for posts, reads or attachment uploads (decision
  above), because ids alone would show audit readers who wrote to whom, past D16's deletion of
  the thread. Thuong confirms, or asks for id-only rows with that trade-off accepted.

  empty and error states named above) ship extrapolated from deck primitives and are listed for
