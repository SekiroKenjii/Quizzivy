Foundations

Everything on the other sheets is assembled from this page. The tokens are copied verbatim from web/src/index.css; the components are the shadcn/ui new-york primitives constrained by spec §12. If a screen needs something that is not here, that is a signal to add it here first — not to invent a one-off.

1 · Colour

Zinc surfaces, charcoal primary, semantic colour only where it carries meaning. Nothing decorative gets a hue. The token names below are the only way a component may reference a colour — that is what makes the dark theme (P1) a token swap rather than a rewrite. Try the Tối toggle above: no rule in the kit changes.

Forbidden by §12

Decorative gradients · glassmorphism / backdrop blur · pulsing rings · glow · radii above rounded-lg · emoji in UI chrome · brand colour on a non-semantic surface. A green badge means the answer was right, never “this row is nice”.

4 · Motion, focus, and the rules that survive review

Motion

150ms ease-out on state change. No entrance animation — a list that fades in is a list that arrives late. Dialogs appear; they do not spring. prefers-reduced-motion disables the rest.

The one exception worth having: the timer’s minute change is not animated at all, because a moving clock pulls the eye away from the question.

Focus & keyboard

A 2px neutral ring, offset 2px, on every interactive element. Never a coloured glow. Tab order follows reading order.

⌘K command palette A–E chọn đáp án ←→ chuyển câu F đánh dấu

Touch & reach

Student targets are ≥44px and live in the bottom third of the phone screen. Admin targets may be 28–32px because the teacher has a mouse and a 768px+ viewport (§1.1).

Nothing destructive ever sits next to a frequently-tapped control. “Nộp bài” and “Thoát” are never adjacent.

F-11 Side columns — two roles, one width each

Earlier drafts of this deck drew the right-hand panel at three widths (G-01 and A-04 at 20rem, G-07 at 24rem, S-08 at 18rem) because each board was drawn for its own screen. Four widths for one component is drift, not design: it gives the next screen no answer to “how wide is this?”. There are two roles here, and each gets one width. The boards above have been redrawn to match.

Panel · right · 20rem

w-80 border-l p-5 space-y-5 — details what is selected in the middle, or summarises what the middle is building. G-01 summary · G-07 student · A-04 question settings · S-08 navigator.

Rail · left · 14rem

w-56 border-r p-4 space-y-5 — filters what the middle shows. Narrower on purpose: it holds checkboxes and chips, and at panel width it would be mostly empty. A-06 bank filters.

Both run the full height of the content area beside the scroll, never inside it, and scroll by themselves when their own content is taller than the screen — a filter rail that scrolls away with the results is a rail you cannot reach while reading them. Neither is sticky; sticky is what you reach for when the column is in the wrong place.

F-12 Admin at 768 — what the side columns do §8 · minimum supported width

§8 sets 768px as the admin minimum and the sidebar already collapses at 1280, so a screen has the full 768 to spend. Measured at that width, every list, both detail screens and the assignment form are fine: their tables scroll inside their own card and nothing is clipped or unreachable. One screen is not. The builder puts an outline (18rem), an editor and a settings panel (20rem) side by side, which leaves the editor 145px — a prompt field four words wide. This board is the rule that fixes it, and it is deliberately narrow in scope: nothing else needed changing.

Rail · stays

14rem out of 768 leaves 544 for the middle, which the question bank's table uses without complaint. A filter rail that disappears takes the results' meaning with it, so it stays drawn at every supported width.

Panel · becomes a sheet

Below 1024px the panel leaves the layout and its content opens from a button in the screen's own bar, unchanged. This is S-08's move — the take-test navigator is a rail from lg up and a sheet below it — applied to the other column role. Nothing is hidden: the same fields, one tap away.

Bar · labels drop to icons

A bar carrying a title field, a status, a save state and four buttons cannot hold them all at 768. The secondary actions keep their icon and lose their label below lg, exactly as S-05's flag button already does, so the primary action and the title stay legible.

Measured, not assumed. The rule above comes from walking every admin route at 768 and asking one question per element: does anything sit past the viewport with no scrollable ancestor? On the lists the answer was no — the tables were already scrolling inside their cards, so the earlier report of a clipped table was wrong. Only the builder failed, and only once a question was selected.
What this is not. Not a phone layout. §1.1 keeps the admin side desktop-and-tablet, and 768 is the floor, not a target to design toward. The panel still belongs beside the content wherever it fits; the sheet is what happens when the room runs out.
F-13 Side columns resize — one handle, one remembered width per role every screen with a rail, a panel, the shell's sidebar, the builder's outline

F-11 gave each role one width so the next screen had an answer to “how wide is this?”. The answer is still one width per role — the teacher now picks it. Every side column carries a handle on its inner edge: a 6px hit area over the border, a col-resize cursor, and a 2px line that only shows on hover or while dragging, so at rest the column looks exactly as F-11 drew it. Drag it, or focus it and use the arrow keys (16px a step, Home and End for the limits); double-click puts the deck's width back. The width is remembered in the browser per role, not per screen: a panel dragged wider on G-07 is the same width on A-04, because it is the same component.

The max is also bounded live: a side may not grow past the point where the middle column would fall under 24rem, which keeps F-12's builder rule true at every width the teacher can reach.

Why per role and not per screen. A width remembered per screen would give the teacher twelve widths to keep in their head and the deck twelve answers again — the drift F-11 removed. One width per role means the panel is the panel everywhere, only now at the width this teacher reads best at.
Keyboard is not an afterthought. The handle is a separator with a value, so it is reachable by Tab, announces its width, and moves by arrow key. A resize that only exists for a mouse would fail §12's accessibility bar on the one control that changes the whole layout.
The sheet is untouched. Below 1024px the panel is a sheet (F-12) and has no handle: a sheet is as wide as the viewport lets it be. The remembered width waits for the next wide screen.
F-14 Icon sizes — one scale, chosen by where the icon sits §12 · every screen

§12 says “16px dense / 20px nav” and left the rest to taste, and taste drifted: the running app was measured on 2026-09-05 and an icon inside a badge rendered at 24px (lucide's default, because nothing sized it), the 24px button carried a 12px icon where this deck draws a 28px button with a 14px one, and a table cell held 14, 16 and 24 depending on the screen. The scale below is what the deck already drew most often in each place — 57 of 59 table buttons at 14, 39 of 43 badge icons at 12, 88 of 89 small buttons at 16 — written down so the next screen does not have to count. One rule of thumb generates it: an icon is about half the height of the control it sits in, and never taller than the line of text beside it.
